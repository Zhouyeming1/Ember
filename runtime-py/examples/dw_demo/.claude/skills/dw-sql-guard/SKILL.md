# 改 SQL 之前，先弄清会波及谁

数仓里最贵的事故不是语法错误——那个会直接报错、跑不起来。真正贵的是**静默的口径
变化**：改一个字段、下游炸一片，而且动手前没人知道；等业务发现数字不对，可能已经
错了一周。血缘如果只存在于老员工的脑子里或一份必然过期的文档里，这件事就迟早会
发生。

所以在这个项目里动 SQL，按三步走。

## 1. 改之前：查影响面

先确定你要动的是哪张表、哪个字段，然后查谁在依赖它。

```
sql_impact(table="dws.dws_user_gmv_d")
```

要精确到字段就带上字段名（字段级会逐层接力，能一路追到最下游的报表字段）：

```
sql_impact(table="dws.dws_user_gmv_d", column="gmv")
```

看输出时注意三件事：

- **下游层数越多，越要先和下游对齐**。影响到 ADS 层（报表 / 接口 / BI 直连的表）
  就是业务可见的变更，不是改完就完事。
- **出了「索引不完整」或「解析失败」的提示，就不是"没有下游"，而是"没查全"**。
  这时别下结论，把范围缩小到具体文件再查。
- 表名可以不带库名，会按后缀匹配并注明匹配方式；但**带库名更可靠**——同名表在多库
  下会撞。

## 2. 改的时候：注意这几类会咬人的写法

- **分区列不能被函数包住**：`WHERE substr(dt,1,6)='202401'` 会让分区裁剪彻底失效，
  退化成全表扫描。改成 `dt BETWEEN '20240101' AND '20240131'`。
- **`INSERT OVERWRITE` 分区表一定要写 `PARTITION (col)`**。漏了不是"少写一句"，
  是把**所有历史分区**覆盖掉。这是本仓最危险的一处，`sql_lint` 会按错误级报出来。
- **别自读自写**（`INSERT OVERWRITE t ... FROM t`）：Hive 下行为依赖执行顺序，
  可能读到写了一半的数据。落中间表再换入。
- **分区过滤别写死日期**：调度脚本里写死 `dt='2024-01-01'` 不会报错，只是每天跑的
  都是那一天。用调度变量 `${bizdate}` / `$[yyyyMMdd]` / `{{ ds }}`。

## 3. 改完：跑一遍规范检查

```
sql_lint(path="jobs/dws_user_gmv_d.sql")
```

它按 `rule_id` + 行号给问题清单，分错误 / 警告 / 提示三级。项目觉得某条吵，可以用
`ignore` 关掉：

```
sql_lint(path="...", ignore=["select-star"])
```

靠建表语句才能判的两条（覆盖分区、缺分区过滤）只在工作区里有该表 DDL 时生效——
没有就静默跳过，不猜。

## 拿不准的时候

`sql_lineage` 可以看一个文件或一段 SQL 读了谁、写了谁，字段级也能追来源：

```
sql_lineage(path="jobs/ads_gmv_dashboard.sql", level="column")
```

追一个指标"到底是从哪个字段算出来的"、或者读陌生的数仓脚本时，用这个最快。
